Занятие 30: Вёрстка по макету

Lesson 30: Coding from a Mockup

Процесс работы от Figma-макета до готовой страницы: анализ, разбивка, порядок, pixel-perfect

The workflow from Figma layout to finished page: analysis, breaking into blocks, order, pixel-perfect

В 28-м уроке вы научились читать Figma: размеры, цвета, шрифты, отступы. Отлично. Но это ещё не вёрстка — это только подготовка. Вопрос в том, как перевести макет в рабочий код. Профессионалы делают это по чёткому процессу. Любители открывают VS Code и начинают писать «что-то» — и получают хаос.

Этот урок — методология. Он не про новые свойства CSS, а про порядок действий, который экономит часы и гарантирует pixel-perfect результат. Те же самые HTML и CSS, но применённые в правильном порядке — разница между 6 часами и 2 часами работы.

После этого урока у вас будет универсальный алгоритм: получили макет → прошли по 9 шагам → готов сайт. Этот процесс работает одинаково для лендинга, админки, мобильного приложения. Индустриальный стандарт.

После этого занятия вы сможете:

  • Анализировать Figma-макет за 10-15 минут до написания кода
  • Разбивать макет на секции → компоненты → элементы (атомарный подход)
  • Настраивать проект правильно: папки, шрифты, CSS-переменные с токенами
  • Писать HTML-скелет ДО стилей (разметка отдельно от визуала)
  • Следовать правильному порядку CSS: layout → spacing → colors → details
  • Делать pixel-perfect сравнение через overlay скриншотов
  • Достраивать мобильную версию, если её нет в макете
  • Избегать 10 классических ловушек при вёрстке по макету

In lesson 28 you learned to read Figma: sizes, colors, fonts, spacing. Great. But that's not coding yet — that's just preparation. The question is how to turn the layout into working code. Pros do it with a clear process. Amateurs open VS Code and start writing "stuff" — and get chaos.

This lesson is methodology. Not new CSS properties — the order of actions that saves hours and guarantees pixel-perfect results. Same HTML and CSS, but applied in the right order — the difference between 6 hours and 2 hours of work.

After this lesson you'll have a universal algorithm: got a layout → 9 steps → site is done. Same process for a landing, admin panel, or mobile app. Industry standard.

1. Процесс vs хаос — зачем нужен порядок

1. Process vs chaos — why order matters

Представьте двух разработчиков с одним и тем же макетом. Один хаотично прыгает от элемента к элементу: сначала кнопку стилизует, потом передумал — делает header, потом возвращается к кнопке. В итоге 6 часов работы и куча мусорного CSS.

Второй сначала 10 минут смотрит на макет: считает секции, выписывает цвета в блокнот. Потом пишет HTML-скелет целиком (без стилей). Потом настраивает layout (flex/grid). Потом детали. Потом адаптив. 2 часа — и готово.

Разница — не в скорости печати. Разница в порядке. Без процесса вы по нескольку раз переделываете одно и то же. С процессом — пишете каждую строчку один раз.

Picture two devs with the same layout. One jumps chaotically from element to element: styles a button, then changes mind and does the header, then goes back to the button. Result: 6 hours of work and a pile of garbage CSS.

The second first looks at the layout for 10 minutes: counts sections, writes colors into a note. Then writes the entire HTML skeleton (no styles). Then sets up layout (flex/grid). Then details. Then responsive. 2 hours — done.

The difference isn't typing speed. The difference is order. Without process — you redo things multiple times. With process — you write each line once.

❌ Хаос
❌ Chaos

6 часов работы:
1. Начал делать кнопку
2. Понял, что нужен header
3. В header ссылку не задал цвет
4. Вернулся к кнопке — переделал
5. Адаптив не работает — переписал header
6. Цвета разные везде — не вынес в переменные

✅ Процесс
✅ Process

2 часа работы:
1. 10 мин — анализ макета
2. 15 мин — tokens (цвета, шрифты)
3. 20 мин — HTML-скелет целиком
4. 30 мин — layout (flex/grid)
5. 30 мин — детали
6. 15 мин — адаптив
7. 10 мин — pixel-perfect проверка

Ремонт квартиры. Плохой процесс: положили плитку, поняли, что провод забыли → сняли плитку, проложили провод, положили заново. Хороший процесс: сначала электрика, потом штукатурка, потом плитка, потом мебель. Каждый этап делается один раз. В вёрстке то же самое: HTML → layout → детали → адаптив.

Apartment renovation. Bad process: laid the tile, realized you forgot the wiring → removed tile, laid wire, re-tiled. Good process: electrical first, then plaster, then tile, then furniture. Each stage is done once. Same in coding: HTML → layout → details → responsive.

2. Шаг 1: Анализ макета (10-15 минут)

2. Step 1: Analyze the layout (10-15 min)

Не открывайте VS Code сразу. Сначала откройте только Figma — и 10-15 минут просто смотрите. Ваша задача — понять макет целиком, увидеть повторяющиеся элементы, продумать структуру. Это самый недооценённый шаг. Все профи его делают, все новички пропускают.

Don't open VS Code yet. First open Figma only — and for 10-15 minutes just look. Your job: understand the layout as a whole, spot repeating elements, think through structure. The most underrated step. All pros do it, all beginners skip it.

3. Шаг 2: Разбивка на блоки

3. Step 2: Break into blocks

Большая проблема «кажется сложным» решается разбивкой на мелкие части. В вёрстке это называется атомарный подход: макет → секции → компоненты → элементы. Каждый уровень проще предыдущего.

The "it looks complicated" problem is solved by breaking into small parts. In coding it's called the atomic approach: layout → sections → components → elements. Each level is simpler than the previous.

Иерархия: Страница (Layout) └─ Секции (Hero, Features, Footer...) └─ Компоненты (Card, Button, Form...) └─ Элементы (h1, p, img, input...) └─ Атомы (цвет, шрифт, отступ) Сверху вниз — всё сложнее. Снизу вверх — всё проще. Писать снизу вверх: сначала атомы (tokens), потом элементы, потом компоненты, потом секции.
Hierarchy: Page (Layout) └─ Sections (Hero, Features, Footer...) └─ Components (Card, Button, Form...) └─ Elements (h1, p, img, input...) └─ Atoms (color, font, spacing) Top-down — increasingly complex. Bottom-up — increasingly simple. Code bottom-up: atoms (tokens) first, then elements, then components, then sections.

Пример анализа: у вас лендинг ресторана. Что вы видите?

  • Секций: 6 (header, hero, about, menu, contacts, footer)
  • Компонентов: 3 (card меню, button, form)
  • Элементов в card: 4 (image, h3, p, price)
  • Атомов: 5 цветов, 1 шрифт с 4 размерами, 3 размера отступов

Итог: вы пишете один .card и один .btn — и используете их 10 раз на странице. Меняете дизайн — правите в одном месте.

Analysis example: you have a restaurant landing. What do you see?

  • Sections: 6 (header, hero, about, menu, contacts, footer)
  • Components: 3 (menu card, button, form)
  • Elements in card: 4 (image, h3, p, price)
  • Atoms: 5 colors, 1 font with 4 sizes, 3 spacing sizes

Result: you write one .card and one .btn — used 10 times on the page. Change the design — edit in one place.

5. Шаг 4: HTML-скелет без стилей

5. Step 4: HTML skeleton without styles

Ключевая идея: сначала разметка, потом стили. Напишите весь HTML страницы без единой строчки CSS. Страница будет выглядеть «уродливо» — это нормально. Ваша задача — создать правильную структуру: семантические теги, классы, иерархию.

Почему так? HTML — это смысл. CSS — это внешний вид. Смешивать их в голове при написании — значит путать оба. Пишите сначала смысл, потом оформление.

Key idea: markup first, styles later. Write the entire page HTML without a single line of CSS. The page will look "ugly" — that's fine. Your job is to create the right structure: semantic tags, classes, hierarchy.

Why? HTML is meaning. CSS is appearance. Mixing them in your head while writing means confusing both. Write meaning first, styling later.

<body>
    <header class="header">
        <a href="#" class="logo">Brand</a>
        <nav class="nav">
            <a href="#features">Features</a>
            <a href="#about">About</a>
            <a href="#contact">Contact</a>
        </nav>
        <a href="#" class="btn btn-primary">Get Started</a>
    </header>

    <section class="hero">
        <div class="container">
            <h1>Headline</h1>
            <p>Subheading text...</p>
            <a href="#" class="btn btn-primary btn-lg">CTA</a>
        </div>
    </section>

    <section class="features">
        <div class="container">
            <h2>Features</h2>
            <div class="features-grid">
                <article class="feature">
                    <img src="icons/speed.svg" alt="">
                    <h3>Fast</h3>
                    <p>Description...</p>
                </article>
                <!-- ещё 2 -->
            </div>
        </div>
    </section>

    <footer class="footer">...</footer>
</body>
Семантика важна! Не пишите всё через <div>. Используйте <header>, <nav>, <main>, <section>, <article>, <footer>. Это важно для SEO и screen-readers.
Semantics matter! Don't write everything with <div>. Use <header>, <nav>, <main>, <section>, <article>, <footer>. Critical for SEO and screen readers.

Не пишите inline-стили в HTML. «Я быстренько поставлю style="color: red"» — это технический долг. На странице 500 таких подсказок «быстренько» — и вы не можете найти нужный стиль. Всё в CSS-файле. Всегда.

Don't write inline styles in HTML. "I'll just quickly put style="color: red"" — that's tech debt. On a page with 500 such "quick" fixes — you can't find the right style. Everything in the CSS file. Always.

6. Шаг 5: CSS — layout (flex/grid)

6. Step 5: CSS — layout (flex/grid)

HTML готов, страница выглядит ужасно (поток тегов сверху вниз). Теперь первый слой стилей — layout. Не цвета. Не шрифты. Только размещение элементов на странице: flex, grid, ширины, отступы между секциями.

Результат этого шага: страница имеет правильную структуру (колонки, ряды, секции разделены), но всё ещё выглядит «черновой» — без цветов и красивой типографии.

HTML is ready, page looks terrible (stream of tags top-down). Now the first layer of styles — layout. Not colors. Not fonts. Just element placement on the page: flex, grid, widths, section spacing.

Result of this step: page has the right structure (columns, rows, sections separated), but still looks "drafty" — no colors and no pretty typography.

/* base.css — сброс + контейнер */
* { margin: 0; padding: 0; box-sizing: border-box; }

body {
    font-family: var(--font-primary);
    line-height: 1.6;
}

.container {
    width: 90%;
    max-width: 1200px;
    margin: 0 auto;
}

/* style.css — секции */
.header {
    display: flex;
    align-items: center;
    justify-content: space-between;
    padding: var(--space-sm);
}

.nav {
    display: flex;
    gap: var(--space-md);
}

.hero {
    min-height: 80vh;
    display: flex;
    align-items: center;
}

.features-grid {
    display: grid;
    grid-template-columns: repeat(3, 1fr);
    gap: var(--space-md);
}

Правильный порядок внутри одного селектора:

.card {
    /* 1. Layout */
    display: flex;
    flex-direction: column;
    gap: 16px;

    /* 2. Размеры */
    width: 100%;
    max-width: 400px;
    min-height: 300px;

    /* 3. Отступы */
    padding: 24px;
    margin: 0 auto;

    /* 4. Визуал */
    background: white;
    border-radius: 12px;
    box-shadow: var(--shadow-md);

    /* 5. Типография */
    font-size: 16px;
    color: var(--color-text);

    /* 6. Интерактив */
    transition: transform 0.3s;
}

Порядок помогает читать код и находить нужное.

Correct order inside a selector:

.card {
    /* 1. Layout */
    display: flex;
    flex-direction: column;
    gap: 16px;

    /* 2. Size */
    width: 100%;
    max-width: 400px;

    /* 3. Spacing */

    /* 4. Visual */
    background: white;
    border-radius: 12px;
    box-shadow: var(--shadow-md);

    /* 5. Typography */
    font-size: 16px;
    color: var(--color-text);

    /* 6. Interactivity */

Order helps read code and find things.

7. Шаг 6: CSS — детали (цвета, шрифты, отступы)

7. Step 6: CSS — details (colors, fonts, spacing)

Layout готов — теперь наводим красоту. Цвета фона, цвета текста, шрифты, размеры, тени, скругления. Здесь макет «оживает». Каждую деталь сверяйте с Figma: кликнули на элемент в макете — перенесли цвет/размер в CSS.

Layout is ready — now we polish. Background colors, text colors, fonts, sizes, shadows, rounding. Here the layout "comes alive". Check each detail against Figma: click the element in the layout — copy color/size to CSS.

/* Типография */
h1 {
    font-size: var(--fs-h1);
    font-weight: 700;
    line-height: 1.2;
    color: var(--color-text);
}

h2 {
    font-size: var(--fs-h2);
    font-weight: 600;
    margin-bottom: var(--space-md);
}

/* Секции */
.hero {
    background: linear-gradient(135deg, var(--color-primary), var(--color-primary-dark));
    color: white;
    padding: var(--space-xl) 0;
}

.features {
    background: var(--color-bg);
    padding: var(--space-xl) 0;
}

/* Компоненты */
.feature {
    background: white;
    padding: var(--space-md);
    border-radius: var(--radius);
    box-shadow: var(--shadow-sm);
    text-align: center;
}

.feature h3 {
    font-size: var(--fs-h3);
    margin: var(--space-sm) 0;
}

.feature p {
    color: var(--color-text-muted);
}
Всё через переменные! Не пишите color: #3B82F6 — пишите color: var(--color-primary). Если дизайнер поменяет основной цвет — правите одну строку в tokens.css.
Everything via variables! Don't write color: #3B82F6 — write color: var(--color-primary). If the designer changes the primary color — edit one line in tokens.css.

8. Шаг 7: Интерактив (hover, transition, :focus)

8. Step 7: Interactivity (hover, transition, :focus)

Статичная страница собрана. Теперь делаем её живой: hover на кнопках и ссылках, hover-эффекты на карточках, :focus на инпутах, transition для плавности. Без этого шага сайт выглядит «мёртвым» и дешёвым.

Static page is done. Now make it alive: hover on buttons and links, card hover effects, :focus on inputs, transition for smoothness. Without this step, a site looks "dead" and cheap.

/* Кнопки */
.btn {
    transition: all 0.2s ease;
    cursor: pointer;
}
.btn:hover {

Макет часто не показывает hover. Дизайнер рисует только базовое состояние. Hover-эффекты — на ваше усмотрение. Золотой стандарт: кнопки поднимаются (translateY(-2px)), карточки поднимаются и усиливают тень, ссылки меняют цвет. Всё с transition.

Layouts often don't show hover. Designer draws only the base state. Hover effects are up to you. Gold standard: buttons lift (translateY(-2px)), cards lift and strengthen shadow, links change color. All with transition.

9. Шаг 8: Адаптив (если нет мобильного макета)

9. Step 8: Responsiveness (when there's no mobile mockup)

В 90% макетов дизайнер рисует только десктоп (1440px). Мобильный — ваша ответственность. Не бойтесь — есть чёткие правила, как адаптировать десктоп в мобильный.

In 90% of layouts designers only draw desktop (1440px). Mobile is your responsibility. Don't panic — there are clear rules for adapting desktop to mobile.

Правило «один ряд → стопка». Всё, что на десктопе в ряд — на мобильном в стопку. Флекс → flex-direction: column. Грид → grid-template-columns: 1fr. Простое правило, покрывает 80% случаев.

"Row → stack" rule. Everything horizontal on desktop — stacks on mobile. Flex → flex-direction: column. Grid → grid-template-columns: 1fr. Simple rule, covers 80% of cases.

10. Шаг 9: Pixel-perfect проверка

10. Step 9: Pixel-perfect check

Страница готова — но соответствует ли она макету? Нужна проверка. Pixel-perfect означает: каждый пиксель вашей страницы совпадает с макетом (допуск ±2px). Именно это проверит дизайнер при ревью.

Page is done — but does it match the layout? You need to check. Pixel-perfect means: every pixel of your page matches the mockup (±2px tolerance). That's what the designer checks at review.

3 способа сравнения:

3 comparison methods:

  1. Side-by-side: Figma на пол-экрана, браузер на другой. Визуальное сравнение. Самый быстрый.
  2. Overlay-скриншоты: сделайте скриншот Figma и браузера, откройте в Paint/Photoshop/tldraw, наложите друг на друга с opacity 50%. Все расхождения видны сразу.
  3. PerfectPixel extension: Chrome-расширение «PerfectPixel by WellDoneCode». Показывает Figma-скриншот полупрозрачно поверх вашей страницы.
  1. Side-by-side: Figma on half the screen, browser on the other. Visual comparison. Fastest.
  2. Screenshot overlay: screenshot Figma and browser, open in Paint/Photoshop/tldraw, layer them at 50% opacity. All discrepancies visible instantly.
  3. PerfectPixel extension: Chrome extension "PerfectPixel by WellDoneCode". Shows the Figma screenshot semi-transparent over your page.

Чеклист pixel-perfect:

  • Шрифт и размеры заголовков совпадают?
  • Цвета совпадают (HEX)?
  • Отступы между блоками такие же?
  • Ширина контейнера такая же?
  • Border-radius и тени совпадают?
  • Картинки не размыты (2x для Retina)?
  • Иконки в SVG, не PNG?
  • Работает на мобильном (375px) и десктопе (1440px)?

Pixel-perfect checklist:

  • Font and heading sizes match?
  • Colors match (HEX)?
  • Spacing between blocks same?
  • Container width same?
  • Border-radius and shadows match?
  • Images not blurry (2x for Retina)?
  • Icons in SVG, not PNG?
  • Works on mobile (375px) and desktop (1440px)?
