# Отчёт по проекту «Мониторинг объявлений → Telegram»

Дата: 2026‑01‑24

## 1) Что мы сделали (результат)
Собран и реализован сервис, который:
- принимает ссылки подписок (поиск/категория/город) от пользователей через Telegram-бота или API;
- проверяет источники по расписанию с **честным лимитом 1–10 RPS на пользователя**;
- парсит результаты, сохраняет объявления в Postgres;
- делает **дедупликацию** (одно объявление не присылается повторно для той же подписки даже после рестартов);
- отправляет уведомления в Telegram через очередь;
- работает в Docker Compose и масштабируется воркерами;
- имеет админку в браузере (Django Admin) на русском;
- имеет внутренние эндпоинты наблюдаемости (stats/metrics) + Prometheus-формат.

Ключевое: архитектура сделана так, чтобы выдерживать нагрузку за счёт очередей и горизонтального масштабирования воркеров (целевой порядок — 150+ клиентов).

---

## 2) Архитектура и компоненты
### Сервисы
- **backend (Django + DRF + Admin)**
  - хранит пользователей, профили Telegram, подписки, объявления, связи подписка↔объявление;
  - делает дедуп и формирует события уведомлений;
  - отдаёт API для бота и воркеров;
  - отдаёт internal stats/metrics.

- **scheduler**
  - читает активные подписки;
  - планирует проверки и кладёт задания в Redis Streams;
  - обеспечивает справедливость: лимит считается **на пользователя**, внутри пользователя подписки имеют «вес».

- **worker (N экземпляров)**
  - читает задачи из Redis Streams (consumer group);
  - делает HTTP-запрос к источнику, парсит страницу;
  - отправляет найденные items в backend;
  - поддерживает ретраи/backoff на сетевых/5xx ошибках;
  - при `HTTP 429/403` аккуратно фиксирует ошибку (и backend ставит подписку на авто‑паузу).

- **bot (aiogram)**
  - интерфейс пользователя: /add /list /status /del /on /off /rps /pause /unpause;
  - читает очередь уведомлений Redis Streams и отправляет сообщения;
  - поддерживает команды вида `/cmd@BotName` (для групп) и ID вида `<15>`.

- **redis**
  - Streams: `stream:checks` (задачи), `stream:notify` (уведомления);
  - consumer groups + XAUTOCLAIM → at‑least‑once обработка.

- **postgres**
  - источник истины и дедуп (уникальные связи подписки с item).

## 3) Как работает end‑to‑end (поток данных)
1) Пользователь пишет боту `/add <url> [rps]` → bot вызывает backend.
2) backend создаёт подписку, привязанную к Telegram‑профилю пользователя.
3) scheduler периодически формирует задания «проверить url» и пишет их в `stream:checks`.
4) worker забирает задания из `stream:checks`, скачивает страницу источника, парсит items.
5) worker отправляет items в backend (`/api/v1/worker/report/`).
6) backend сохраняет новые items, делает дедуп, пишет события в `stream:notify`.
7) bot читает `stream:notify`, запрашивает у backend «готовый текст уведомления» и отправляет его в Telegram.

Устойчивость: Redis Streams + consumer groups дают at‑least‑once, а дедуп в Postgres гарантирует отсутствие дублей.

## 4) Надёжность и наблюдаемость
### Защита от блокировок источника
- При `HTTP 429/403` подписка автоматически ставится на паузу (backoff по попыткам) — это защита от «добивания» IP, а не обход капчи.
- Есть ручная пауза `/pause` и снятие `/unpause`.

### Трассировка задач
- У задач есть `job_id` и `enqueued_at`, backend сохраняет их в подписке и считает `job_latency_ms`.

### Метрики/статусы
- Статусы подписок: `last_check_at`, `last_success_at`, `last_item_at`, `last_error`, `consecutive_errors`, `paused_until`.
- Внутренние эндпоинты:
  - `/api/v1/internal/stats/` — Streams/groups/consumers/heartbeats + snapshot метрик.
  - `/api/v1/internal/metrics/` — JSON counters/observations.
  - `/api/v1/internal/metrics.prom` — Prometheus text format.

## 5) Масштабирование под 150+ клиентов
- Горизонтально масштабируется `worker`:
  - `docker compose up -d --scale worker=N`
- Увеличение пропускной способности достигается:
  - увеличением числа воркеров;
  - настройкой лимитов/таймаутов;
  - (опционально) настройкой прокси для исходящих запросов воркера к источнику.

Важное: ограничение **1–10 RPS** применяется на уровне пользователя (TelegramProfile), а `rps_limit` у подписки выступает как «вес/приоритет» внутри бюджета пользователя.

Это список задач, которые логично закрывать вместе с тестированием в РФ (на живом IP/инфраструктуре):

1) **Интеграционное тестирование на реальном источнике**
   - прогнать 10–30 подписок на реальных ссылках;
   - замерить задержку «публикация → Telegram»;
   - проверить авто‑паузу и восстановление после блокировок.

2) **Нагрузка/масштабирование**
   - прогон по демо‑источнику: 150 пользователей × 1–10 RPS (с контролем очередей);
   - подобрать `worker`-масштаб и лимиты таймаутов.

3) **Операционная готовность (24/7)**
   - настроить мониторинг Prometheus (или аналог) по `/metrics.prom`;
   - добавить алерты: рост pending, рост ошибок, отсутствие heartbeats.

4) **Прод‑полировка (по желанию / отдельно)**
   - отдельная админ‑панель/кабинет клиента (вместо только Telegram);
   - касса/оплаты/тарифы и автопродление;
   - переход бота на webhook и масштабирование бота (если понадобится);
   - более «богатый» парсинг конкретных источников (под конкретные страницы/категории).
